## 1. 官方核心与工作台边界

保持官方 CLI、app-server、Harness、工具执行、安全策略、上下文管理、认证和历史存储实现不变。工作台通过公开协议使用它们；产品 UI 需求不能成为改写核心执行语义的理由。

已新增独立 `workbench/` 顶层目录，未加入上游 Rust workspace、未修改上游依赖锁文件。以下是完整模块规划；当前已实现 contracts、protocol-adapter、desktop-host 的 stdio 生命周期和合成 tests；并实现首个 Electron 窗口、受限 IPC、合成 UI 及 domain 历史/审批状态；其他能力仍待实现：

```text
workbench/
  desktop-host/       进程、窗口、文件选择、系统集成、Git/PTY 等受控能力
  ui/                 页面、组件、交互、主题、可访问性
  protocol-adapter/   版本化请求、事件归一化、能力门控
  contracts/          同版本生成协议、版本清单、稳定/实验清单
  domain/             UI 领域状态、恢复与投影，不复制官方 Harness
  host-services/      工作树编排、调度、预览、浏览器等独立服务
  tests/              合成协议记录、契约/集成/界面/升级用例
```

| 模块 | 拥有的职责 | 边界与验收要点 |
| --- | --- | --- |
| 官方核心 | 模型会话、agent turn、工具执行、审批语义、沙箱、凭证管理、原生历史 | 对固定上游提交无产品定制差异；UI 不自造“已批准”或“已完成”事件 |
| 协议适配 | stdio JSONL、初始化、关联请求、通知、服务端请求、schema 版本、能力清单 | 使用自有 clientInfo；消息与 stdio 日志分离；未知事件可诊断且不损坏会话 |
| domain 状态 | thread/turn/item 投影、选择状态、审批待办、分页加载、缓存 | 服务器为执行与历史事实源；本地乐观状态可回滚；不直写官方内部数据库 |
| UI | 选定版本布局、导航、输入、卡片、设置、面板、键盘交互 | renderer 不直接拿凭证或任意 shell；UI 动作对应明确 domain 命令 |
| desktop host | app-server 子进程生命周期、受限 IPC、窗口、文件选择、通知、深链 | host 的用户操作与 agent 执行区分；能力校验不能被 renderer 参数绕过 |
| host services | Git/worktree 生命周期、用户终端、文件预览、调度、浏览器 | 独立接口、数据目录和权限；失败不修改核心语义；不冒充官方云端服务 |
| 服务适配器 | 可用的官方托管服务或外部集成 | 每一项需公开接口与授权证据；未知接口不以内部端点或复制 token 替代 |

M1.c 采用 TypeScript/Node + Electron，决定及限制见 [ADR](desktop-adr.md)。首个合成窗口与隔离 IPC 已验证；PTY、签名分发、可访问性、性能与完整维护成本仍待比较和验收。当前不声称官方使用何种前端栈，也不为选框架提取闭源应用代码。框架选择不应改变上述边界。

## 2. 协议与认证

外部桌面采用独立 `codex app-server` 子进程的 stdio 通道：每次连接一次 `initialize`，成功后发送 `initialized`；使用相同核心版本的生成 schema。Rust 进程内 app-server-client 为 TUI/exec 共享路径，不需要把桌面 UI 塞进这条路径（S-02、S-05）。

连接状态为 stopped → starting → initializing → ready；进程退出后进入有界 draining；主动关闭进入 stopping/disposed；异常进入 disconnected/failed，允许显式重连。请求以 ID 关联响应，服务端请求另设审批/输入处理队列；stdout 仅解协议，stderr 是诊断。不能把进程退出推断为任务成功。

运行状态由官方 thread/turn/item 事件更新。`turn/start` 的返回不等于完成；等待终态通知并核对历史。断线后重新读取 thread/turn/item、未决请求和已知运行状态；不要自动重放可能已执行的 turn、命令、审批或文件写入。传输序列号只是本地记录，不假定协议提供全局事件序列；对重复与延迟事件按实体 ID 和协议语义处理。

历史与持久化分工：官方核心拥有会话历史；工作台独立存储窗口、面板、排序偏好及 host 服务元数据。只有协议已定义的项目、分区、附件等资源才使用对应接口；不得修改官方数据库来模拟缺失 API。迁移需要版本号、备份、失败回退，备份不含凭证。

认证采用官方管理的 ChatGPT OAuth：读取账户状态，必要时通过 `account/login/start` 发起官方登录，由官方核心保存与刷新登录状态。用户已说明 Pro 登录可用，不要求另购 API；本轮未尝试登录或验证额度。UI 不读取 `auth.json`、浏览器 cookie 或系统凭证库；`chatgptAuthTokens` 在源码标注仅供内部且不稳定，不作为重建接口。账户、模型和额度按真实服务结果呈现，不能把 unknown 显示成 0。

## 3. 稳定、实验与 host 能力

这里“稳定”只指固定版本未标记实验的相应方法，仍需核验参数字段和实际服务支持；不是对未来版本的永久兼容承诺。

| 类别 | 固定基线例子 | 使用策略 |
| --- | --- | --- |
| 官方普通协议 | thread/start/resume/fork/read、turn/start/steer/interrupt、thread/turns/list、thread/items/list、threadSection、附件、model/list、config、审批 | 首个闭环优先接入；逐字段生成类型及契约用例 |
| 官方实验协议 | project/*、thread/search、thread/queue/*、thread/timeline/list、turn/settings/update、process/*、thread/realtime/*、remoteControl/* | 单独模块与白名单；显式 opt-in；逐功能可关闭；错误/字段变更不拖垮普通流程 |
| 公开库、非完整桌面 API | WorktreeManager、Git 工具 | 可以独立 host wrapper 复用或遵循公开实现，但先验证线程绑定与生命周期，不假定存在完整 RPC |
| 自建桌面能力 | 面板、文件预览、通知、用户 PTY、调度、浏览器 UI、升级器 | 标记为待实现；与核心协议分离；每项真实操作及恢复验收 |
| 未核实公开接口 | 官方云端 Chat/Work/同步/分享、完整跨主机 handoff、部分专属插件服务 | 保留目标并登记阻碍；只读官方公开材料核实后才做接入承诺 |

实验开关是连接能力，不能假装每条请求都独立协商。建议主连接默认关闭实验；需要项目等能力时由受控配置启用相应连接的实验能力，并在 adapter 内继续按方法和字段白名单门控。开启实验不意味着允许全部实验方法，也不代表账户获得服务权限。关闭后保留数据并给出不可用原因，不能用静默丢数据来降级。

基线易错点：

- `thread/rollback` 已移除；使用基线 `thread/revert` 的真实语义。会话历史回退不等于 Git 文件撤销。
- `thread/turns/list`、`thread/items/list` 方法在本基线未标记实验；仍需检查具体字段。不要继续沿用旧版分类。
- `thread/items/read`、`thread/readState/update` 是此前 main 对照中的后续候选，不能当作 `0.162.1` 已有接口。未读呈现可在工作台维护本地状态，并如实标注同步限制。
- `command/exec` 遵守服务端沙箱；实验 `process/spawn` 是无 Codex 沙箱的独立进程。集成终端是用户主动的 host 能力，agent 不能借它绕过自身审批。
- WorktreeManager 的创建/列表/移除不自动提供可恢复归档。移除前的数据快照、未跟踪与忽略文件处理、冲突检查和恢复是独立里程碑。
- 原生 userVerification 依赖专门 host、硬件和能力条件；改写 clientInfo 为官方名字不能获得资格，不采用此做法（S-04）。

## 4. 全量 UI 核对方法

先补 V-01 至 V-11，再建视图目录、导航图、组件清单、设计 token 和交互状态表。每个目标记录：产品视图、环境（本地/云端）、前置条件、入口、状态变化、退出与恢复、数据来源、错误、键盘/焦点、证据编号。不要只照静态首页截图写组件。

视觉对照固定窗口、主题、语言、缩放和合成数据。测量侧栏、标题区、内容区、输入区、分隔与面板尺寸，再核字体、间距、颜色、图标、滚动、hover/focus/disabled。截图差异阈值在首套参考评审时确定并记录；现在没有参考，不填写虚构像素值或相似度。动态时间/光标/内容区域需定义合理遮罩，但不可遮住布局缺陷。

Chat、Work、Codex 使用独立视图与后端能力映射；共享外壳与组件并不合并它们的历史、执行位置或权限。范围决策前，保留全部待核对行；普通本地 Codex 流程可先开发，最终“全功能完成”仍被未闭合的范围及服务项阻挡。

## 6. 上游升级策略

1. 保留 upstream 官方 remote 与用户 origin；记录当前核心版本、SHA、schema 哈希、工作台版本、UI 参考版本和实验白名单。
2. 每次升级选择明确官方稳定 tag，在升级分支核实 tag→commit；检查签名状态并如实记录。不要把 main、预发布或桌面版本号当作核心稳定版。
3. 先合并官方核心更新，再在独立适配层处理 schema、方法、字段、事件和能力变化；不自动覆盖用户工作或运行破坏性 reset。
4. 由新核心生成匹配 schema，diff 普通/实验/移除项；对未知枚举、可空字段、审批、历史分页、启动、登录、关闭做契约回归。生成步骤在实现阶段执行，本轮未运行。
5. 运行合成契约、获准的本地端到端、视觉和数据迁移测试。实验功能单独报告；旧记录回放和新写入后恢复都要覆盖。
6. 核对核心目录相对目标上游提交无定制修改，更新 manifest/文档；先本地验收再考虑提交或发布。推送、发布按届时用户指令执行。
7. 回退必须同时考虑二进制、schema 和数据兼容性。新版本已写入不向后兼容数据时，使用升级前受控备份恢复；不可只降级二进制然后继续写旧数据。
